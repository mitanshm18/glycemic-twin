# M5 — PostgreSQL + FastAPI backend: learning note

## What was built

```
browser / curl ──HTTPS──► FastAPI (api/src/twin_api)
                            ├─ auth.py        sessions, roles, CSRF, audit log
                            ├─ routers/       /api/v1/...  (Pydantic in, Pydantic out)
                            ├─ service.py     ── calls ──► twin_core.twin.build_state / simulate
                            ├─ repository.py  DbRecordSource: rows ─► PatientRecord
                            └─ registry.py    model bundles + support profiles (M4 checks)
                                  │
                           SQLAlchemy ORM ─► PostgreSQL 16 (schema from Alembic migration 0001)
                                  ▲
       twin-api ingest ───────────┘  reads data/processed/m1/*.parquet + M1/M2 manifests
```

## The PostgreSQL schema

Sixteen tables in four groups. **Who:** `users`, `sessions`. **What was observed:** `patients`,
`clinical_observations`, `cgm_readings`, `wearable_minutes`, `meals`, `meal_labels`, all copied from
the M1 clean tables and stamped with the `ingestion_runs` row that loaded them. **Which model:**
`model_versions`, `support_profiles`. **What the twin produced:** `twin_states`, `predictions`,
`what_if_runs`, `replay_sessions`; and `audit_log` for who did what. Constraints hold the project's
rules inside the database itself, for example "a meal has a label if and only if it is
frozen-usable" and "only one model is active".

## ORM vs database

The **database** is the source of truth: tables, constraints, indexes, enum types. The **ORM**
(SQLAlchemy) is a Python description of those tables that lets code build queries safely without
string-pasting SQL. We keep them honest with a test that compares the migrated database with the ORM
models and requires zero differences.

## Migrations

A migration is a versioned script that changes the schema (Alembic, `api/migrations/versions/`).
A fresh database is built by running every migration in order (`make db-migrate`), never by
`create_all`. A test creates an empty database, migrates up, checks the schema, migrates all the way
down (every table and enum type gone), and up again.

## FastAPI request lifecycle

1. The request arrives; FastAPI matches the route and validates the input with its Pydantic model
   (extra fields are rejected; `"5"` is not accepted where a number is required).
2. Dependencies run: a database session is opened; the session cookie is looked up; the role is
   checked; for POSTs the CSRF header is checked.
3. The route calls the service (which calls twin_core) and commits.
4. The result is serialized through the response model, so the output shape is guaranteed.
5. Any error becomes the single `{"error": {...}}` shape; audit entries are written in their own
   transaction, so a refusal is recorded even though the request failed.

## Authentication and session flow

Login checks the Argon2id hash (a deliberately slow, memory-hard hash; the password itself is never
stored). The server creates a random session token, stores only its SHA-256, and sends the token in
an HttpOnly, SameSite=Strict cookie that JavaScript cannot read. It also returns a CSRF token that the
client must echo in `X-CSRF-Token` on every POST, which blocks forged cross-site requests. Logout
revokes the session row, so the cookie stops working immediately. Five wrong passwords lock the
account for 15 minutes, and an unknown username gets exactly the same answer as a wrong password.

## API → twin_core architecture

The API does not know how features, labels, personalization or risk work. It turns database rows
into a `PatientRecord` and hands it to `build_state` / `simulate` with the active model. The response
of `/patients/{id}/twin` *is* twin_core's `TwinState` (ADR-017), unchanged; the what-if response *is*
`ScenarioResult`. So the numbers the API shows are exactly the numbers the tested engine produces.

## Model registry

`twin-api register-m3` loads each M3 bundle, runs the contract check and the M4 compatibility check,
and stores its identity: type, feature set, the ordered 45 columns, contract version and hash,
features and labels hashes, the training data hash, threshold, params, prior, and the file's
SHA-256. One version is active. At serving time the API re-hashes the file; a changed or incompatible
artifact is refused. The what-if engine needs the **training-support profile** built from the real
M2 dataset; it is stored and linked only to models trained on that exact dataset.

## Provenance

Every patient row points to its ingestion run, which records the M1 source manifest hash, config
hashes and the M2 dataset hash. Every twin state stores its record hash, the meals whose outcomes it
used, the model identity and config hashes (all inside the state document), and is keyed by its own
content hash, so asking the same question twice returns the same stored snapshot.

## Why the Digital Twin core stays database-independent

The twin is the scientific core; the database is plumbing. Keeping twin_core pure means the exact
same code runs in training, tests, notebooks and the API; it can be tested without any server; and
changing the storage (or adding a different API) cannot change a single prediction.
