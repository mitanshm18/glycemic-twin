# M2 — Features, labels and leakage: learning note

## What was built

The meal-level dataset that every model will be trained and tested on, plus automated proof that no
feature can see the future.

```
M1 clean tables (data/processed/m1)
  └─ twin_core.features.history_from_tables   one ParticipantHistory per person, NATIVE CGM only
  └─ twin_core.features.meal_features          about 40 features per meal at its start time t0,
                                               plus the latest timestamp it read
  └─ twin_ml.dataset.folds                     5 participant-level folds, stratified, pinned to CSV
  └─ twin_ml.dataset.leakage                   checks L1-L6; a hard failure stops the run
  └─ data/processed/m2/dataset.parquet         one row per meal: ids, features, outcomes, fold
  └─ data/reports/m2_dataset.md                availability, fold balance, check results
```

Plus `twin_core.personalization`, the shrinkage maths the twin will use to learn each person, which
M3 fits inside each fold.

## Why it exists

A model is only as honest as its inputs. The most common way a health-prediction project fools itself
is leakage: some input quietly contains information from after the moment of prediction, so test
scores look great and real use disappoints. M2 makes leakage structurally hard (the history object
simply doesn't contain interpolated CGM) and then checks for it anyway, in several independent ways.

## What you need to understand

**One function for training and serving.** `meal_features(history, meal)` is the only place features
are defined. The offline pipeline calls it for 1,663 meals; the API (M5) will call it for one live
meal. If training and serving computed features differently ("train/serve skew"), the model would
receive inputs it never saw in training.

**How "past-only" is guaranteed, in three layers:**

1. **By construction:** CGM history holds native readings only; every window is sliced with explicit
   rules (≤ t0 for CGM, < t0 for wearable minutes and earlier meals, window closed for past outcomes).
2. **By bookkeeping:** every call returns the latest timestamp it read; check L2 fails if any meal read
   anything after its start.
3. **By re-computation (the strongest):** check L3 recomputes features for 100 meals from a history
   *cut off at t0*. If any value differs, some feature was using the future. The tests plant a leaky
   feature (reading glucose 5 minutes after the meal) and confirm the run stops.

**Future invariance.** "Adding data from the future must not change today's features." Tests check
this on random histories; a property-based version (Hypothesis) runs on your machine.

**Why a past meal's label is usable only after 120 minutes.** At 13:30 you do not yet know whether
the 12:30 lunch will cross 180 by 14:30. Counting it would use information that doesn't exist yet.
The tests include a meal whose window closes one minute after t0: it must not count.

**Participant-level folds.** All of a person's meals go in the same fold. If a person's Monday meals
were in training and their Tuesday meals in testing, the model could recognize the person (their
HbA1c, their baseline glucose) rather than predict the meal, and scores would be inflated. The folds
are stratified, so each has a similar mix of healthy, prediabetes and T2D people, and they are pinned
to a file so they cannot drift.

**Shrinkage, the core of personalization.** A person with 2 meals, both positive, should not be told
"100% risk". Beta-binomial shrinkage starts from the population rate and moves toward the person's own
rate as evidence accumulates: p = (positives + α) / (meals + α + β). α and β come from training
participants only, fitted inside each fold (ADR-014), so a test person's outcomes never shape their
own starting point.

**The single-feature AUROC screen (L6).** If one feature alone predicts the label almost perfectly
(AUROC > 0.95), that is suspicious: it may be a disguised copy of the outcome. It is flagged for
review, not treated as an automatic failure, because a genuinely strong feature is possible. On the
tiny synthetic fixture it flags HbA1c, correctly: one fake person's meals are all negative and the
other two people's all positive.

## Interview questions you should be able to answer

1. What is data leakage? Give two concrete examples from glucose prediction and how this project
   blocks each.
2. What is train/serve skew, and how does one shared feature function prevent it?
3. Explain the three layers that guarantee features use only the past. Which one would catch a bug in
   the other two?
4. Why can't the personal positive rate include a meal eaten 60 minutes ago?
5. Why split folds by participant instead of by meal? What would happen to the scores otherwise?
6. Explain beta-binomial shrinkage with numbers: population rate 40%, α + β = 10, a person with 3
   meals, all positive.
7. Why are the population priors fitted inside each fold rather than once on everyone?
8. Why is missing METs "unknown" and not 0, and how does the model see the difference?
9. What does a single-feature AUROC of 0.99 suggest, and what would you do about it?
10. Why is the label on minute rows while features use native readings (ADR-013)? What is the
    limitation, and how will SA-1 measure it?
