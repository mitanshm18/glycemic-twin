# M1 — Data foundation: learning note

## What was built

A reproducible pipeline that reads the CGMacros download without ever changing it, proves it read the
right files, checks their shape, cleans them with written-down rules, computes the frozen label for
every meal, and writes an audit that counts everything.

```
CGMacros ZIP or folder (read-only)
  └─ source.py      finds bio.csv and CGMacros-XXX.csv files; same paths for ZIP or folder
  └─ manifest.py    SHA-256 of every CSV; checks the ZIP against PhysioNet; pins/verifies a lock file
  └─ contracts.py   exact column names, required columns, timestamp parsing -> fails loudly on drift
  └─ clean.py       per participant, using twin_core rules:
        duplicates -> CGM range -> native grid -> wearable -> meals -> frozen outcomes
  └─ audit.py       counts: participants, coverage, native readings, meals, exclusions, positives
  └─ report.py      data/reports/m1_audit.{json,md} and the generated block in docs/data-card.md
```

The rules themselves live in `packages/twin_core`, a library with no database or web code, because
the API will reuse exactly the same code in M5. The thresholds live in
`data/configs/cleaning.v1.yaml` and `data/configs/labels.v1.yaml`.

## Why it exists

Every later result (model accuracy, the twin's state, the demo) is only as trustworthy as this layer.
Four failure modes are designed out here:

1. **Using the wrong or modified data:** checksums and a pinned manifest.
2. **Silent schema drift:** a renamed column would become all-empty and quietly change results; the
   contract stops the run instead.
3. **Cleaning decided after seeing results:** every threshold is written down first, with its reason,
   and its effect is counted.
4. **Future information in the past:** CGM minute values are interpolated, so the value "just before"
   a meal can secretly contain the reading taken after it. Native-reading detection prevents that.

## What you need to understand

**Raw, staged, clean.** Raw files are never edited. Staging renames and types columns but keeps every
value and its source row. Cleaning applies rules and records which rule touched which row. If a rule
changes, you rerun from raw; you never patch the cleaned data by hand.

**Checksums.** SHA-256 turns a file into a 64-character fingerprint; change one byte and the
fingerprint changes completely. PhysioNet publishes the fingerprint of the ZIP, so matching it proves
you have their exact file. An extracted folder cannot be compared with PhysioNet, so the first run
records every file's fingerprint in a lock file and every later run must match it.

**Native-grid detection, in plain terms.** The Dexcom sensor writes a whole number every 5 minutes. The
dataset fills the four minutes in between with straight-line guesses, which are usually fractions like
121.4. If you group the minute rows by "minute number mod 5", one of the five groups is almost entirely
whole numbers: those are the real readings. The code finds that group separately for each stretch of
data between gaps, because after a sensor change the group can move. As a check, it also tests that the
in-between minutes really lie on the straight line joining two real readings.

**Why this matters for leakage.** Suppose a meal starts at 12:00, with real readings at 11:58 and
12:03. The dataset's 12:00 value is 60% of the way from 11:58 to 12:03, so it already contains
information from 12:03, after the meal started. A model given that value would look better in testing
than it can ever be in real life.

**The frozen label and the added exclusions.** The label and "usable meal" definition are exactly the
ones frozen in Phase 0A (minute rows, 180 mg/dL, 120 minutes, 80% coverage, no meal within 120
minutes). On top of that, the training and evaluation set drops meals with no real reading in the 15
minutes before the meal, meals already above 180 before eating, and meals with unusable macros. The
audit reports both sets, and the viability rule on both.

**Reconciliation.** The audit compares its numbers with the Phase 0A exploratory audit. Frozen
quantities must match exactly; if they don't, either the new code or the old script has a bug, and you
find out before training rather than after.

**Tests on synthetic data.** The tests use a small fake dataset built with known answers: a sensor
change, a duplicate timestamp, a 900% Amount Consumed, a fiber value larger than carbs, and so on.
It is test data only; it never trains a model or produces a reported number.

## Interview questions you should be able to answer

1. Why should raw data never be edited, and how does this project prove it wasn't?
2. What is a SHA-256 checksum, and what exactly does matching PhysioNet's value prove? What doesn't it
   prove for an extracted folder?
3. What is a data contract, and what bug does it prevent that a unit test on cleaning code would miss?
4. Explain how you detected which CGM rows are real sensor readings. What would make the method fail,
   and what happens then?
5. Give a concrete example of how an interpolated glucose value leaks future information.
6. What is the difference between a hard validity rule and a judgment threshold? Give one of each from
   this project and defend the judgment one.
7. Why are Amount Consumed values never used as a feature, even the valid ones?
8. Why is missing METs "unknown" rather than 0? What would go wrong with 0?
9. Why keep the frozen label on minute rows instead of switching it to native readings?
10. How would you know if your reimplementation of the Phase 0A audit had a bug?
