# M4 — The Digital Twin engine: learning note

## What was built

```
PatientRecord (raw observations, M1 shapes)          TwinRuntime (frozen configs + M3 bundle + support profile)
        │                                                     │
        └──────────── build_state(patient_id, as_of) ─────────┘
                        1. cut everything at as_of
                        2. recompute outcomes; keep closed windows only
                        3. meal_features (M2)      → 42 base inputs
                        4. personal_features (M3)  → 3 personal inputs, bundle's prior
                        5. bundle.predict_proba     → calibrated risk
                        ▼
                   TwinState (immutable, hashed, with provenance)
                        │
                   simulate(..., {"carbs_g": -30}) → ScenarioResult (bounded, non-causal)
                   diff_states(a, b)               → what changed and why
```

## What a Digital Twin means in this project

A digital twin here is a **living computational model of one person's glucose response to meals**.
For each person, at any moment, it keeps a state built from their real observations: clinical
baseline, recent glucose and heart rate, what they ate, and how their glucose responded to their past
meals. From that state it predicts whether the current meal will push Dexcom glucose above 180 within
two hours, and it can answer bounded "what if this meal had fewer carbs" questions. It updates as new
data arrives and becomes more personal over time.

## Why it is not a 3D avatar

"Digital twin" is often shown as a 3D body. That would be decoration here: nothing in our data
describes anatomy. What makes it a twin is that it mirrors the person's **state and behaviour** over
time (a model plus a state that updates from their data, predicts, and can be queried with
scenarios), the way an engineering twin mirrors a turbine's condition rather than its paint.

## How state is constructed

`build_state` takes the person's record and cuts it at `as_of`. From that cut it computes, with the
exact M1–M3 functions: static clinical context (observed vs derived fields marked), personal baselines
(overnight glucose, resting heart rate, time in range), current physiology (last native glucose,
slopes, heart rate, activity), recent history (last 3 hours, meals in the last 24 h, recent closed meal
outcomes), the current meal (the latest meal whose 2-hour window is still open, or a proposed meal at
`as_of`), the personal response summary, the risk with its uncertainty flags, data freshness and
provenance. The state is a frozen object; its `state_id` is a hash of its content.

## The lifecycle

- **COLD_START:** no meal window has closed yet. The twin knows nothing personal, so p_personal equals
  the population rate and the personal weight is 0. It can still predict, from glucose, the meal and
  clinical data.
- **WARMING:** at least one closed meal, but the person's own evidence does not yet outweigh the
  population (weight < 0.5, or fewer than 3 meals).
- **PERSONALIZED:** weight ≥ 0.5 and at least 3 closed meals: the person's own history now dominates
  the personal estimates.

The phase only moves forward, because closed evidence only accumulates as time moves forward.

## How personalization works

Two shrinkage estimates, from the person's closed past meals only (M2/M3 logic, unchanged):
p_personal = (positives + α) / (meals + α + β), and a rise offset (how much more their glucose rises
than the population rise model predicts), multiplied by the weight w = n / (n + k). α, β and k come
from the PopulationPrior **stored in the model bundle**, fitted on training participants only. With no
history the estimates equal the population; with more history they move toward the person.

## Why `as_of` matters

`as_of` is "the moment the twin is looking from". Everything after it is removed before any
computation, and a meal's outcome counts only once its window has closed by then. That is what makes
the twin honest in a replay demo: the state at 13:20 is exactly what could have been known at 13:20.
Tests append wildly different future data and check that the state (and its hash) does not change.

## What provenance means

Every state records what it was built from: a hash of all observations up to `as_of`, how many CGM
readings, wearable minutes and meals it used, which past meals' outcomes fed personalization, which
meal is being predicted, the latest timestamp any value used (always ≤ `as_of`), the config hashes, the
engine version and the model identity (name, feature set, contract hash, training data hash). Anyone
can trace a number back to its inputs and model.

## What-if limitations

- **Association, not causation.** "Fewer carbs → lower risk" is what the model learned from
  observational data; it is not proof that eating fewer carbs causes a lower peak for this person.
- **Only what the model can see.** Meal macros of the current meal, and pre-meal activity only when
  METs were recorded. Post-meal walks cannot be simulated: the model has no post-meal inputs.
- **Bounded.** Each change has a maximum; every changed input must stay inside the range seen in
  training (1st–99th percentile), otherwise the answer is `out_of_support` with no number.
- **Never medical.** Medication, insulin, diagnosis and treatment levers are refused.

## How train/serve skew is prevented

Train/serve skew is when the model sees inputs at serving time computed differently from training.
Here: the twin calls the same feature and personalization functions as M2/M3; it uses the prior,
preprocessing and calibrator stored in the bundle (nothing refitted); the runtime refuses a bundle
whose contract, columns or config hashes differ; and a test rebuilds all 45 inputs for every fixture
meal through the twin and checks they equal the M2 dataset plus the M3 personal features exactly.

## What to say in the jury presentation

"Our twin is a per-person state that updates from real CGM, wearable, meal and clinical data. It is
deterministic and versioned: the same data at the same moment gives the same state and the same hash,
and every prediction carries the exact model version and the observations it used."
