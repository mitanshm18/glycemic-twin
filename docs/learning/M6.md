# M6 — Flagship clinician frontend: learning note

## What was built

A Next.js workspace in `web/` over the M5 API, plus a small read-only adapter in the API
(`routers/insights.py`, `explain.py`). Screens:

| Route | Purpose |
| --- | --- |
| `/login` | Username/password sign-in (inline validation, password toggle, Caps Lock hint) and "Continue with Google" for admin-linked Google accounts; explains expiry, sign-out and every Google failure; forwards an already signed-in user without showing the form |
| `/patients` | Participants with group, scorable meals, lifecycle, last estimate, recording span; search, population/lifecycle/risk filters, sortable columns (`aria-sort`); phone layout stacks rows into cards |
| `/patients/[id]` | The Twin: current state → why → glucose + meals (prediction → reality) → personal response → what-if → evolution (learning curve + diff) → provenance |
| `/patients/[id]/record` | Baseline clinical fields with observed/derived provenance, then a day-by-day chronology (native CGM chart, meals with frozen outcomes, wearable totals) |
| `/model` | Scope, cross-validated metrics with 95% CIs, calibration curve, decisions at the threshold, per-fold spread, all M3 runs and paired comparisons, global SHAP importance, limitations, registry |

## How a screen gets its data

`lib/api/client.ts` is the only place that calls `fetch`. It sends cookies, attaches
`X-CSRF-Token` to every POST (fetching one from `/auth/csrf` if the page was reloaded), retries once
on `CSRF_FAILED`, turns the API's `{"error": {code, message}}` into `ApiError`, and broadcasts a
session-expired event on 401 so the shell can send the user to `/login?expired=1&next=…`.
`lib/api/queries.ts` wraps each endpoint in a TanStack Query hook with a stable key. Observations are
cached indefinitely (retrospective data never changes); twin states are cached per `(patient, as_of,
meal)`; 4xx errors are never retried.

`lib/errors.ts` maps each error code to wording specific to what the page was showing, so the user
never sees "Something went wrong".

## The Twin page, section by section

- **Current state.** Two zones divided by a rule: *Model estimate* (risk dial with the threshold tick,
  status tag, the outcome in words) and *Measured* (latest native Dexcom value, trend, age), then
  lifecycle, uncertainty, freshness, the moment, the model and the current meal. Values that change
  when you step to another meal count to their new value and briefly highlight.
- **Why this risk?** `GET /twin-states/{id}/explanation`. The served model recomputes exact
  per-feature contributions for the stored inputs (TreeSHAP for XGBoost, coefficient × input for
  logistic regression). Diverging bars show direction and relative size; each row has the value and a
  plain-language description; the arithmetic line shows baseline → raw log-odds → calibrated
  probability. Labelled *model association, not causal*.
- **Glucose and meals.** Native readings only (interpolated minutes are never drawn). The chart shows
  what the twin saw up to its moment; *Reveal outcome* draws the next two hours and compares the
  estimate with the observed peak and the frozen labels.v1 outcome (true alert / false alarm / miss /
  true quiet). The model predicts a probability, not a trajectory, so no predicted curve is drawn.
- **Personal response.** Lifecycle stepper (cold start → warming → personalized), evidence weight
  against the personalization threshold, closed meals and positives, personal vs population rate,
  latest closed windows.
- **What-if.** Sliders for the current meal's carbohydrate, fiber, protein and fat and pre-meal
  active minutes (only when the wearable records METs). Changes are debounced and sent to
  `POST /what-if`; the server validates, checks the training-support profile and answers. Outside
  support there is no estimate, and the panel shows which input left the trained range.
- **Evolution.** *Trace* rebuilds the twin at the start of every scorable meal in order (each a real
  API state) and plots personal weight, personal rate, population rate and risk. *What changed* diffs
  any stored snapshot against the current one with twin_core's own `diff_states`.
- **Provenance.** State ID, model version, source-record hash and latest source time, with a sheet
  listing every hash and count.

## Authentication architecture

Two ways in, one session. Both end with the same server-side session: a random 256-bit token whose
SHA-256 is stored in `sessions`, sent to the browser as the HttpOnly cookie `twin_session`
(`SameSite=Lax`, `Secure` outside local http, path `/`, 8 hours). Every API request looks the
session up, so sign-out and expiry take effect at once. Every POST also carries the session's CSRF
token in `X-CSRF-Token`; that header, not SameSite, is what stops cross-site requests.

```
password:  /login form ──POST /auth/login──▶ Argon2id check ──▶ session + cookie (+ CSRF token in the body)
google:    "Continue with Google" ──GET /auth/google/start──▶ accounts.google.com ──▶ GET /auth/google/callback
           ──(server ⇄ Google token endpoint)──▶ provisioned identity? ──▶ session + cookie ──303──▶ destination
```

Accounts are provisioned by an administrator (`twin-api create-user`); there is no self sign-up.

## Google sign-in (OpenID Connect)

- **Authorization code + PKCE (S256) + state + nonce**, entirely on the server. The browser only
  follows redirects; it never sees an ID, access or refresh token.
- **State** is 256 random bits, stored in `oauth_flows` only as its SHA-256 and also in an HttpOnly
  cookie scoped to `/api/v1/auth/google`. The callback requires the query state to equal the
  cookie's (so a link carrying someone else's state fails), the row to exist (single use: it is
  deleted on first use) and to be under 10 minutes old.
- **Token endpoint**: the server posts the code, client secret and PKCE verifier to
  `https://oauth2.googleapis.com/token` over verified TLS and keeps only the ID token. Per OIDC Core
  §3.1.3.7(6), TLS to the token endpoint establishes the issuer; the claims are still checked:
  `iss`, `aud`/`azp`, `exp`, `iat`, `nonce`, `email_verified`, optional Workspace `hd`.
- **Provisioning rule**: a Google account signs in only through a `user_identities` row an admin
  created (`twin-api link-google USERNAME EMAIL`). The first sign-in binds Google's stable `sub`;
  afterwards the `sub` must match, so a re-used address on another Google account is refused.
  Unknown accounts get "not linked to a clinician account"; nothing is created. Inactive or locked
  users are refused.
- **Errors** come back as `/login?auth_error=<code>` with a specific message for each code
  (not configured, cancelled, expired/used link, exchange failed, token invalid, email unverified,
  wrong domain, not provisioned, identity mismatch, account unavailable).
- **Secrets and logs**: the client secret is a `SecretStr` read from the environment and used only
  in the server-to-server request; no secret or setting reaches the browser bundle. Audit entries
  record the outcome with the email's domain and SHA-256 only; the callback's query string (code,
  state) is redacted from access logs.

Setup: create a Google Cloud OAuth client of type *Web application*, add the redirect URI exactly
(`http://localhost:3000/api/v1/auth/google/callback` locally), put the values in `.env`, restart
the API, then link each clinician: `uv run twin-api link-google alice alice@clinic.org`.

## Session restoration and the auth lifecycle

| Moment | What happens |
| --- | --- |
| First load of a workspace URL without a cookie | the Next middleware redirects to `/login?next=<url>` before any page code runs |
| Any full page load with a cookie (reload, deep link, new tab) | `AuthGate` asks `/auth/me`; while waiting it shows a quiet placeholder (never the form, never a redirect) |
| `/auth/me` = 200 | the page renders; nothing else changes |
| `/auth/me` = 401 (expired, revoked) | `/login?next=<url>&expired=1` → "Your session ended"; after sign-in, back to `<url>` |
| `/auth/me` unreachable | "Can't confirm your session" with Retry; the user is not signed out |
| Visiting `/login` while signed in | the page checks first and forwards to `next` without showing the form |
| Any API 401 mid-session | the same expiry redirect (one listener, `twin:session-expired`) |
| Sign out | server revokes the session; the client clears every cached query and goes to `/login?signed_out=1`; expected 401s are not reported as expiry; the back button cannot reopen the workspace |
| Sign in (either method) | a fresh session token (no fixation); any previous user's cached data is cleared |

Why a reload used to fail: the cookie was `SameSite=Strict`. A browser withholds Strict cookies from
a top-level page load that began on another site (a link clicked in a terminal, chat or e-mail)
and from reloads of that page, so the middleware saw "no cookie" and redirected, while in-app
`fetch` calls still carried the cookie. Lax sends the cookie on top-level navigations; the gate
removes any remaining dependence on timing.

## Design system

`styles/tokens.css` is the single source of design decisions: semantic OKLCH colours for light and
dark, an 11–52 px type scale (Inter for text, JetBrains Mono for numbers and identifiers), a 4 px
spacing scale, radii, shadows and motion durations. Meaning is carried by dedicated tokens (`--model`
purple for estimates, `--observed` for measurements, `--risk-*` / `--success-*` / `--warning-*`) and
always paired with text or a glyph, so nothing depends on colour alone. Components use tokens only,
which is why dark mode needed no per-component work.

## Motion principles

Motion is used only to explain a change: of page, of status, of data, or of feedback.

| Where | What moves | Duration |
| --- | --- | --- |
| Route change | page fades up 4 px (changes of `?at=` do not re-trigger it) | 200 ms |
| Sidebar / patient tabs | active indicator grows in | 200 ms |
| Patient rows | background on hover/focus; chevron slides in | 120–200 ms |
| Risk dial on opening a Twin | number and arc rise together from 0 after the page settles | 900 ms (150 ms delay) |
| Risk status | the new status label fades in as the number settles | 200 ms |
| Glucose chart | measured line draws on for each new window; meal markers arrive in sequence | 900 ms; 40 ms stagger |
| Prediction → reality | recorded data revealed along the timeline with a running clock; then predicted, recorded peak, outcome and verdict in order | 2 s; 120–160 ms steps |
| What-if | baseline → scenario bars; delta counts to each new server answer | 320 ms |
| Twin diff | changed fields highlight in turn | 40 ms stagger |
| Sheets, toasts | slide/fade in and out | 200–360 ms |
| Skeleton → content | content fades in | 200 ms |
| Theme change | whole-page cross-fade (View Transitions) | 260 ms |

Rules: one easing (`--ease-standard`), transform and opacity only, no bounce, parallax, scroll
effects or idle animation. `prefers-reduced-motion: reduce` removes every movement above (the dial
shows its value at once, the reveal completes instantly, pages appear without fading) while every
state change stays visible. Tested in unit tests (`motion.test.tsx`) and end to end.

## Theme architecture

Light, Dark and System. The preference is stored in `localStorage` (`twin-theme`, a per-browser
convenience). An inline script in `<head>` resolves it (System → `prefers-color-scheme`) and sets
`data-theme` before first paint, so there is no flash. `ThemeProvider` keeps it in sync and follows
OS changes live while System is selected. Every colour is a semantic token with a light and a dark
value; components never pick raw colours, so both themes are complete by construction. Dark is a
blue-graphite canvas, not an inversion: tints, chart grids and status colours are re-balanced per
theme. All text tokens meet WCAG AA (4.5:1) on every surface and tint in both themes; this was
enforced after axe found muted text at 4.1–4.4:1 on tinted panels.

## Accessibility

Skip link; one `h1` per page; landmarks (`main`, named `nav`s, `search`); every control has a
name; form fields are labelled, validation messages are tied to their field with
`aria-describedby` and `aria-invalid`; the password toggle is a named `aria-pressed` button;
segmented controls and the theme switcher follow the radio-group pattern; tooltips are reachable
by keyboard and exposed as descriptions; sheets are native `<dialog>` (focus trapped, Escape
closes, focus returns to the opener); charts are focusable with arrow-key readouts and a text
summary; tables use `caption`, `scope` and `aria-sort`; the patient list supports `/` to search and
arrow keys between rows; status never relies on colour alone (every tone has a label and a glyph);
reduced motion is fully honoured. Automated: axe (WCAG 2.1 AA) on every page in light, dark and
phone layouts in the end-to-end suite, plus component tests for names, descriptions and keyboard
behaviour.

## Responsive behaviour

Checked at 1440 (desktop), 1280 (laptop), 820 (tablet) and 390 px (phone), light and dark, with an
automatic horizontal-overflow check on every page. Desktop: sidebar + content column (max 76 rem).
Below 1024 px: sticky top bar with the navigation (theme, account) in a sheet; the Twin's section
nav stays sticky beneath it; the sign-in page stacks a short intro above the form. Below 768 px:
patient rows become labelled cards with their own sort control (the table header is hidden), driver
bars move under their text, the what-if result follows the levers, provenance stacks. Charts keep
their clinical frame and readable labels rather than shrinking.

## Limitations

- The clinical record renders one day at a time; a multi-week overview is not built.
- The learning-curve trace issues one request per scorable meal (typically 20–40); it shows progress
  and can be re-run, but is not instant.
- Meal photos exist in CGMacros but are not ingested (ADR-018), so none are shown.
