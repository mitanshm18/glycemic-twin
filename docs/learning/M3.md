# M3 — Training, calibration and honest evaluation: learning note

## What was built

The code that trains the models and measures them without fooling itself.

```
data/processed/m2/dataset.parquet
  └─ twin_ml.training.design     model inputs: exactly the ADR-015 columns, prior fitted per fit
  └─ twin_ml.training.models     pipelines (preprocessing inside), baselines, Platt calibrator, threshold
  └─ twin_ml.training.cv         nested participant-level CV + audit log of every fit
  └─ twin_ml.training.metrics    AUROC, PR-AUC, Brier, calibration, participant bootstrap
  └─ twin_ml.training.explain    TreeSHAP on held-out folds only
  └─ twin_ml.training.bundle     model + preprocessing + calibrator + prior + provenance
  └─ data/reports/m3_evaluation.md, data/processed/m3/ (OOF, SHAP, model bundles)
```

## What Logistic Regression does here

It adds up the 45 inputs, each multiplied by a learned weight, and turns the sum into a probability
with the S-shaped logistic function. Before that, inside the pipeline, missing values are filled with
the training median (plus a 0/1 "was missing" column) and every input is standardized, so weights are
comparable "per standard deviation". The L2 penalty (the `C` grid) keeps weights small, which matters
with only ~30 target participants. It is the transparent reference: if XGBoost can't beat it, the
extra complexity isn't earning its place.

## What XGBoost does here

It builds a few hundred small decision trees (depth 2–3), each correcting the errors of the ones
before. Trees capture interactions a linear model can't, for example "high carbs matter more when
pre-meal glucose is already high". It handles missing values natively (each split learns which way
missing goes). Monotone constraints force risk to only go up with g_last and carbs and only go down
with fiber, so the model can't learn a physiologically absurd shape from noise.

## Why participant-level CV is required

The twin will be used by people it has never seen. If a person's meals were split between training
and test, the model could memorize that person (their HbA1c, their usual glucose) and the score would
measure recognition, not prediction. Every split here, outer and inner, is by participant. And it is
**nested**: the outer test fold is locked away while the inner folds choose hyper-parameters,
calibration and the threshold, so none of those choices is tuned to the test fold.

## What calibration means

A model is calibrated if, among meals it gives 70%, about 70% actually go above 180. Ranking well
(AUROC) and being calibrated are different: a model can rank perfectly and still say 95% when the truth
is 60%. For a twin that shows a probability to a person, calibration is what makes the number mean
something. Platt calibration fits a small logistic curve from the model's raw score to the observed
outcome, using predictions the model made on participants it did not train on (inner OOF).
The report shows the calibration slope (1 is ideal; below 1 means too extreme), calibration-in-the-
large (0 is ideal), expected calibration error, and the binned curve.

## AUROC vs PR-AUC vs Brier

- **AUROC:** pick one positive and one negative meal at random; the chance the model ranks the
  positive higher. 0.5 is a coin flip. It ignores the base rate.
- **PR-AUC (average precision):** how precise the model's alarms are across all recall levels. Its
  floor is the prevalence (≈52% in the target group), so always read it against that number. It is
  the pre-registered primary metric because the twin's value is in its alarms.
- **Brier score:** mean squared difference between probability and outcome (0 or 1). Lower is better;
  it rewards both ranking and calibration. The report also shows the "always predict the base rate"
  reference and the Brier skill score relative to it.

## What OOF prediction means

Out-of-fold: every meal gets its prediction from the model of its own outer fold, which never saw that
participant. Pooling those predictions gives one honest prediction per meal, and all metrics are
computed on them. The OOF file is also what later milestones will serve for evaluation participants,
so the demo never shows an in-sample prediction.

## Why SHAP is useful

SHAP splits each prediction into contributions per input that add up exactly to the model's output
(in log-odds): "this meal is high-risk mostly because of 90 g carbs and a pre-meal glucose of 150".
That gives the twin an explanation per meal and a global ranking of what the model relies on, which
also exposes suspicious behaviour (a feature that should not matter dominating). It is still
association: SHAP does not say that changing an input would change glucose.

## Exactly where leakage could happen, and how it is blocked

| Where | The leak | How M3 blocks it | Test |
| --- | --- | --- | --- |
| Model inputs | An outcome column (peak, coverage, label) or an audit count used as a feature | Inputs come only from `contract.columns(...)`; `check_model_inputs` refuses outcome, audit-only, deny-listed or re-ordered columns; the first pipeline step refuses any other columns | `test_model_inputs_exactly_match_adr015`, `test_outcome_columns_never_reach_model_input`, `test_contract_step_refuses_any_other_columns` |
| Outer split | Same person in train and test | Pinned participant folds; OOF rows checked against each fold model's training participants | `test_oof_predictions_are_participant_disjoint_and_complete` |
| Inner tuning | Choosing hyper-parameters on the test fold | Inner folds drawn only from outer-training participants | audit `inner_fit` records; `verify_boundaries` |
| Personalization prior | Test participants' outcomes shaping the population rate used for them | `fit_population_prior` gets only the current fit's training participants; one prior per fit | `test_prior_fit_excludes_test_participants` (spy), `test_test_participants_outcomes_do_not_change_their_prior_or_training_inputs` |
| Personal history | Using a past meal whose 120-min window hasn't closed | `personal_features` counts only windows closed at t0 | `test_personal_features_use_only_closed_history` |
| Preprocessing | Medians/means computed on all data | Imputer and scaler live inside the pipeline, fitted with the model | `test_preprocessing_is_fit_only_on_training_rows` (test fold spiked to 5,000 mg/dL; statistics unchanged) |
| Calibration | Fitting the calibrator on test predictions | Fitted on inner-OOF scores of outer-training participants; records who it saw | `test_calibration_and_threshold_exclude_test_participants` (flipping all test labels changes nothing fitted) |
| Threshold | Picking the cut-off that looks best on the test fold | Chosen on inner OOF, stored before scoring | same test, `test_threshold_is_chosen_before_the_test_fold_is_seen` |
| Explanations | Explaining a meal with a model that trained on it | SHAP computed per outer fold on its own held-out participants | `test_tree_shap_is_oof_only_and_uses_contract_columns` |
| Serving | A bundle trained on other columns | Bundle stores contract version, hash and columns; `load_bundle` refuses mismatches | `test_bundle_has_everything_and_round_trips` |

Every fit writes an audit record (who fitted the prior, the preprocessing/model, the calibrator, the
threshold, and who was scored). `verify_boundaries` checks them all after each run and stops the run
on any violation.

## What to say in the jury presentation

- "Every number is out-of-fold on people the model never saw, with tuning, calibration, threshold and
  personalization all fitted inside the training folds."
- "Our primary metric and comparison were fixed before training: PR-AUC of the model vs the best
  baseline on prediabetes + T2D, with participant-bootstrap confidence intervals."
- "We report healthy participants separately, and we report the ablations, including whether
  personalization helps."

## Limits to state honestly

About 30 target participants: confidence intervals will be wide, and differences between close models
may not be distinguishable. Results are for new participants (regime A) only; the temporal regime is
P1. Everything is association, not causation.
